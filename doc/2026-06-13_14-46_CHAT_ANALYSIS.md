Цей документ містить детальний аналіз архітектури, функціональності та поточного стану системи обміну повідомленнями (чату) в проекті Radio For All (RFA).

## 1. Архітектура та Технологічний стек

Система чату побудована на базі протоколу **WebSocket** з використанням надбудови **STOMP** (Simple Text Oriented Messaging Protocol) та бібліотеки **SockJS** для забезпечення сумісності зі старими браузерами.

### Основні компоненти:
*   **Backend (Spring Boot)**:
    *   `WebSocketConfig`: Конфігурація брокера повідомлень. Використовується Simple Broker для черг та топіків.
    *   `ChatController`: Обробка вхідних повідомлень (`@MessageMapping`) та маршрутизація.
    *   `MessangerService`: Бізнес-логіка, збереження повідомлень та робота зі списками кореспондентів.
    *   `ChatReferenceSingleton`: In-memory сховище для відстеження активних користувачів та кімнат в реальному часі.
*   **Frontend**:
    *   `messenger.html`: Thymeleaf-шаблон, що використовує фрагменти для побудови інтерфейсу.
    *   `chat.js`: Клієнтська логіка на чистому JavaScript (підключення, підписки, рендеринг повідомлень).

## 2. Функціональні можливості

1.  **Публічні кімнати (Public Rooms)**:
    *   Підтримка загальних чатів та чатів окремих радіостанцій.
    *   Автоматична публікація сповіщень про нові треки (через `CreaterService`).
2.  **Приватні повідомлення (Private Messaging)**:
    *   Можливість прямого спілкування між користувачами.
    *   Відстеження статусу прочитання повідомлень.
3.  **Real-time оновлення**:
    *   Миттєве отримання повідомлень через підписки на топіки.
    *   Періодичне оновлення списку активних користувачів та кімнат (кожні 8 секунд).
4.  **Підтримка медіа**:
    *   Можливість передачі HTML-вмісту (наприклад, плеєрів з аудіо-треками) безпосередньо в тілі повідомлення.

## 3. Аналіз безпеки та стабільності

*   **Автентифікація**: Доступ до чату обмежений для авторизованих користувачів (`/chat`).
*   **Heartbeats**: Налаштовано механізм перевірки активності з'єднання (8 секунд), що забезпечує стабільність WebSocket-сесій.
*   **Persistence**: Усі повідомлення зберігаються в базі даних через `ChatRepository`, що дозволяє завантажувати історію при вході.

## 4. Сильні сторони та потенційні покращення

### Сильні сторони:
*   **Інтегрованість**: Чат тісно пов'язаний з музичним контентом (автоматичні пости про треки).
*   **Простота архітектури**: Використання стандартних засобів Spring WebSocket дозволяє легко розширювати функціонал.
*   **Гнучкість**: Підтримка різних типів записів (текст, медіа).

### Потенційні покращення (Recommendations):
1.  **Масштабованість**: Використання `ChatReferenceSingleton` обмежує роботу чату одним вузлом сервера. Для горизонтального масштабування рекомендується перейти на зовнішній брокер (наприклад, **Redis** або **RabbitMQ**).
2.  **Оптимізація трафіку**: Замість повного оновлення списку користувачів кожні 8 секунд через `setInterval`, краще використовувати події `CONNECT`/`DISCONNECT` для інкрементального оновлення списку.
3.  **UX/UI**:
    *   Додати індикатори друку ("User is typing...").
    *   Реалізувати завантаження історії повідомлень (infinite scroll) замість повного завантаження при старті.
4.  **Безпека**: Додати санітизацію HTML-вмісту повідомлень на стороні сервера для запобігання XSS-атакам, оскільки наразі система дозволяє передачу `innerHTML`.

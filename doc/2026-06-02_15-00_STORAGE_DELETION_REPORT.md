# Звіт: План реалізації видалення об'єктів сховища (Storage Objects)
**Дата:** 2 червня 2026 р.
**Статус:** Аналіз та планування

## 1. Аналіз моделі даних та залежностей

Об'єкти сховища (`Store`) інтегровані в багато модулів системи. Видалення об'єкта без перевірки залежностей призведе до помилок відображення контенту або порушення цілісності БД.

### Основні сутності, що використовують `Store`:

| Сутність | Поле посилання | Тип зв'язку | Коментар |
| :--- | :--- | :--- | :--- |
| **Track** | `storeitem` / `storeuuid` | OneToOne / String | Аудіофайл треку |
| **Post** | `coverstoreuuid` | String | Головна ілюстрація посту |
| **AuthorColumn** | `avatarUuid` | String | Фото автора колонки |
| **AuthorArticle** | `coverUuid` | String | Обкладинка статті |
| **PodcastChannel**| `imagechanelstore` | OneToOne | Обкладинка подкасту |
| **PodcastItem** | `enclosurestore` | ManyToOne | Аудіофайл епізоду |
| **PodcastItem** | `imagestoreitem` | ManyToOne | Обкладинка епізоду |
| **Album** | `storeuuidalbumcover`| String | Обкладинка альбому |
| **Documents** | `store` / `storeuuid` | OneToOne / String | Скани документів |
| **Clientdetail** | `profilephoto` | ManyToOne | Фото профілю користувача |

## 2. Аналіз наявних методів

На даний момент функціонал видалення розпорошений:
- `StoreService / StoreFileImplementation.DeleteInStore(Store)`: Видаляє файл з диска та запис з БД. **Не перевіряє залежності.**
- `StoreDependencyService.findDependencies(Store)`: Частково реалізований пошук (Post, Track, Podcast). Потрібно розширити на всі сутності.
- `PodcastService.DetachStoreFromPodcasts(Store)`: Обнуляє посилання у подкастах, постах та треках.
- `CreaterStoreController`: Має початкову реалізацію UI для підтвердження видалення при наявності залежностей.

## 3. Кроки для реалізації видалення за ролями

### Крок 1: Централізація пошуку залежностей
Необхідно оновити `StoreDependencyService`, додавши пошук у:
- `AuthorColumnRepository` (по `avatarUuid`)
- `AuthorArticleRepository` (по `coverUuid`)
- `AlbumRepository` (по `storeuuidalbumcover`)
- `DocumentsRepository` (по `store` або `storeuuid`)
- `ClientdetailRepository` (по `profilephoto`)

### Крок 2: Уніфікація логіки від'єднання (Detachment)
Перенести та розширити метод `DetachStoreFromPodcasts` у `StoreService` (або окремий `StoreCleanupService`), щоб він міг обнуляти посилання у **всіх** вищезгаданих сутностях.

### Крок 3: Реалізація логіки для різних ролей користувачів

#### **Адміністратор (ROLE_ADMIN) / Редактор (ROLE_EDITOR)**
- Має доступ до повного списку файлів у `/admin/storage`.
- Може видалити будь-який файл.
- При спробі видалення файла, що використовується, отримує список усіх залежних об'єктів.
- Варіанти дій:
  1. **Від'єднати та видалити:** Автоматично обнуляє посилання у всіх сутностях та видаляє файл.
  2. **Тільки від'єднати:** Файл залишається, але сутності його більше не використовують.

#### **Креатор (ROLE_CREATER) / Автор (ROLE_AUTHOR)**
- Має доступ тільки до своїх файлів у `/creater/storage`.
- Може видаляти власні файли, якщо вони **не використовуються** в публічному контенті (наприклад, у схвалених треках або опублікованих статтях).
- Якщо файл використовується:
  1. У чернетці (Draft) - дозволити видалення з автоматичним від'єднанням.
  2. У публічному контенті - **блокувати видалення** з пропозицією спочатку замінити ілюстрацію/файл у відповідному пості чи подкасті.

#### **Користувач (ROLE_USER)**
- Може видаляти тільки своє фото профілю через особистий кабінет.
- При завантаженні нового фото старе має автоматично видалятися зі сховища (Cleanup).

### Крок 4: UI/UX покращення
- Додати модальне вікно підтвердження в `mainstore.html`.
- Відображати статус файла: "Використовується" (з посиланням на об'єкти) або "Вільний".

### Крок 5: Автоматичне очищення (Background Task)
Реалізувати `Scheduled` задачу для видалення "сміття":
- Записи `Store`, які позначені як тимчасові та не були прив'язані до жодної сутності протягом 24 годин.
- Файли на диску, для яких немає запису в таблиці `Store`.

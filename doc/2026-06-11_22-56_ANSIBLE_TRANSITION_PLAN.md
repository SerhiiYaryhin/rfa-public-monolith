# План переходу від Shell-скриптів до Ansible для керування радіостанціями
**Дата:** 11 червня 2026 р.
**Час:** 22:56
**Статус:** Стратегічний план рефакторингу інфраструктури

## 1. Аналіз поточного підходу (Shell + Templates)

Поточна система базується на трьох основних компонентах:
1.  **Набір Bash-скриптів** (`createStation.sh`, `preparenginx.sh`, `setadminPSW.sh`).
2.  **Текстові шаблони** (`Server_template/`) з використанням змінних оточення `${VAR}`.
3.  **Зовнішні утиліти** (`envsubst`, `ssh`, `scp`), що викликаються через Java `ProcessBuilder`.

### Основні недоліки:
*   **Відсутність ідемпотентності**: Повторний запуск скрипта часто призводить до помилок (наприклад, "користувач уже існує").
*   **Складність налагодження**: Помилки в середині SSH-сесії важко перехопити та обробити в Java-коді.
*   **Розпорошеність логіки**: Частина конфігурації генерується в Java, частина — в Bash, частина — через шаблони SQL.
*   **Ризики безпеки**: Потреба в прямому SSH-доступі під `root` до серверів БД та черг.

---

## 2. Пропонована архітектура на основі Ansible

Замість того, щоб Java-код знав "як саме" створювати базу чи користувача RabbitMQ, він повинен лише передавати **бажаний стан (Desired State)** у форматі JSON/YAML в Ansible.

### Структура Ansible Role:
*   **rfa_station**: Роль для розгортання конкретної станції.
    *   `tasks/db.yml`: Створення бази та користувача PostgreSQL (модуль `postgresql_db`).
    *   `tasks/mq.yml`: Налаштування VHost та прав у RabbitMQ (модуль `rabbitmq_vhost`).
    *   `tasks/fs.yml`: Створення каталогів та генерація `docker-compose.yml` (модуль `template`).
    *   `tasks/nginx.yml`: Налаштування проксі-сервера (модуль `template` + `service reload`).

## 3. План переходу (Крок за кроком)

### Крок 1: Підготовка середовища
1.  Встановити Ansible на сервері, де працює головний додаток RFA.
2.  Налаштувати SSH-ключі для доступу до цільових серверів під спеціальним технічним користувачем (наприклад, `ansible_worker`) з обмеженими `sudo` правами.

### Крок 2: Перенесення шаблонів
1.  Перетворити шаблони з `Server_template/*.template.*` у формат **Jinja2** (стандарт Ansible). 
    *   Замінити `${STATION_UUID}` на `{{ station_uuid }}`.
2.  Видалити залежність від системної утиліти `envsubst`.

### Крок 3: Розробка Ansible Playbook
1.  Створити головний плейбук `provision_station.yml`.
2.  Реалізувати логіку "всі або нічого": якщо створення бази провалилося, плейбук зупиняється і повертає помилку.

### Крок 4: Модернізація Java-коду (`ServerRunnerService`)
1.  Замінити виклики декількох скриптів на один виклик:
    ```bash
    ansible-playbook provision_station.yml --extra-vars "@vars.json"
    ```
2.  Java-код тепер лише генерує один файл `vars.json` з усіма параметрами станції.
3.  Реалізувати коректну обробку JSON-відповіді від Ansible (callback plugins) для запису результату в історію.

### Крок 5: Тестування та паралельна робота
1.  Запустити Ansible-підхід для нових (тестових) станцій.
2.  Після підтвердження стабільності перевести основний потік створення на Ansible.

---

## 4. Очікувані переваги

1.  **Надійність**: Ansible автоматично перевіряє стан системи. Якщо база вже створена, він просто пропустить цей крок.
2.  **Чистота Java-коду**: Видалення сотень рядків коду, що керують SSH-командами та змінними оточення.
3.  **Масштабованість**: Легко додавати нові сервери для розгортання станцій без зміни коду додатка.
4.  **Безпека**: Використання Ansible Vault для шифрування паролів та відмова від `root` доступу.

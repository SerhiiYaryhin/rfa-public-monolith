# Аналіз логіки StoreSiteController
**Дата та час:** 2026-05-30 17:30
**Файл:** `src/main/java/media/toloka/rfa/radio/store/StoreSiteController.java`

## 1. Загальний огляд
Контролер відповідає за публічний та приватний доступ до медіа-ресурсів (аудіо, зображення, документи), які зберігаються у системному сховищі (Store).

## 2. Аналіз функціональних блоків

### А. Стрімінг аудіо (`/store/audio/{storeUUID}`)
*   **Логіка:** Використовує `ResponseEntity<Resource>` та `FileSystemResource`.
*   **Позитив:** Підтримує HTTP Range запроси автоматично завдяки Spring, що критично для аудіо-плеєрів (можливість перемотування).
*   **Проблема:** Відсутня перевірка прав доступу. Будь-який користувач, знаючи UUID, може отримати доступ до будь-якого аудіофайлу.

### Б. Робота із зображеннями та мініатюрами (`/store/thrumbal/`)
*   **Логіка:** Використовує бібліотеку `Scalr` для динамічного ресайзингу зображень.
*   **Проблема продуктивності:** Мініатюри генеруються **на кожний запит**. Це створює величезне навантаження на CPU при великій кількості відвідувачів. Немає кешування згенерованих мініатюр на диску.
*   **Проблема пам'яті:** Використання `is.readAllBytes()` та `baos.toByteArray()` завантажує весь файл у оперативну пам'ять. Для великих зображень це може призвести до `OutOfMemoryError`.

### В. Доступ до контенту та документів (`/store/content/`, `/store/document/`)
*   **Логіка:** Пряме зчитування файлу в масив байтів.
*   **Критична вразливість (IDOR):** Контролер дозволяє отримувати документи (`/store/document/{storeUUID}`) без перевірки авторизації або власності. Якщо у сховищі лежать приватні документи (контракти, паспорти), вони доступні всім за посиланням.

## 3. Виявлені ризики та недоліки

1.  **Відсутність авторизації (Security Risk):** Майже всі методи є публічними (`@GetMapping` без перевірки `currentUser`). Це дозволяє несанкціонований доступ до приватних медіа-файлів.
2.  **Витік пам'яті (Memory Leak Risk):** Методи `getStoreContent` та `getStoreImage` зчитують весь файл у пам'ять: `byte[] buffer = is.readAllBytes();`. Це погана практика для серверів з високим навантаженням.
3.  **Відсутність кешування (Performance Risk):** Динамічний ресайзинг зображень без кешування результатів швидко виснажить ресурси сервера.
4.  **Дублювання коду:** Методи `getStoreContent`, `getStoreDoc` та `getStoreOgContent` майже ідентичні.

## 4. Рекомендації з покращення

1.  **Безпека:**
    *   Впровадити перевірку власності (аналогічно до `PostService.canUserModifyPost`) для приватних типів контенту (документи, неопубліковані треки).
    *   Розділити публічні ресурси (обкладинки постів, публічні треки) та приватні.
2.  **Продуктивність:**
    *   Використовувати `StreamingResponseBody` або `ResourceRegion` для всіх типів файлів, щоб уникнути завантаження в пам'ять.
    *   Впровадити кешування для мініатюр (зберігати згенеровані файли у папці `cache/` або використовувати CDN/браузерне кешування).
3.  **Рефакторинг:**
    *   Створити єдиний сервісний метод для віддачі файлів через Stream.
    *   Використовувати `MediaTypeFactory` для автоматичного визначення MIME-типу замість хардкоду `audio/mpeg`.

# План оптимізації моделі даних та рекомендації (2026-05-06)

## 1. Аналіз поточного стану
Проведений аналіз структури бази даних та JPA-суттєвостей виявив критичні проблеми з продуктивністю, які призводять до значних затримок при завантаженні сторінок.

### Основні проблеми:
1.  **Масове використання `FetchType.EAGER`**: 
    *   Особливо в класі `Clientdetail`, де майже всі колекції (адреси, контракти, історія, документи, станції, альбоми, треки, пости) завантажуються жадібно.
    *   При завантаженні одного поста завантажується весь граф пов'язаних об'єктів автора, що створює сотні зайвих запитів та перевантажує пам'ять.
2.  **Відсутність індексів**:
    *   Багато полів, за якими виконується фільтрація та сортування (наприклад, `status`, `publish_date`, `roomuuid`), не мають індексів у базі даних.
3.  **Завантаження великих текстових полів у списках**:
    *   При отриманні списку постів або статей з бази вичитується повне поле `postbody` (JSON/HTML), яке може важити мегабайти, хоча для списку потрібен лише заголовок та лід.
4.  **Проблема N+1**:
    *   Через EAGER-зв'язки Hibernate виконує окремі запити для кожної пов'язаної сутності при перегляді списків.

---

## 2. Рекомендації

### 1. Зміна стратегії завантаження (Fetch Strategy)
*   Змінити `FetchType.EAGER` на `FetchType.LAZY` для всіх колекцій та `@ManyToOne` / `@OneToOne` зв'язків.
*   Використовувати `@EntityGraph` або `JOIN FETCH` у репозиторіях лише тоді, коли дані дійсно потрібні для конкретної бізнес-логіки.

### 2. Оптимізація індексів
*   Додати індекси на наступні колонки:
    *   `Post`: `post_status`, `createdate`, `category`
    *   `AuthorArticle`: `status`, `publish_date`, `slug`
    *   `ChatMessage`: `roomuuid`, `touuid`, `fromuuid`, `send`
    *   `Track`: `style`, `uploaddate`

### 3. Використання проекцій та DTO
*   Для сторінок-списків (архіви новин, подкастів тощо) створити інтерфейси-проекції Spring Data JPA, які вибирають лише необхідні поля (id, uuid, title, lead, createdate, coverUuid).
*   Це дозволить уникнути завантаження важких полів `postbody` з бази даних.

---

## 3. План робіт (Step-by-Step)

### Етап 1: Термінові зміни (Refactoring JPA)
1.  **Clientdetail**: Перевести всі `List<...>` на `FetchType.LAZY`.
2.  **Post**: Змінити завантаження `PostCategory` та `Clientdetail` на `LAZY`.
3.  **Track/Store**: Змінити завантаження `Clientdetail` на `LAZY`.
4.  **Security**: Перевірити сутність `Users` та її зв'язки.

### Етап 2: База даних (Indexing)
1.  Створити міграцію (або оновити `@Table(indexes = ...)` у коді) для додавання індексів на поля пошуку та сортування.
2.  Перевірити `uuid` колонки — вони мають бути унікальними та проіндексованими (вже частково зроблено).

### Етап 3: Оптимізація запитів (Query Optimization)
1.  Аудит репозиторіїв `PostRepositore`, `TrackRepositore`, `AuthorArticleRepository`.
2.  Впровадження `Pageable` всюди, де це можливо (якщо ще не зроблено).
3.  Створення проекцій для головної сторінки та списків.

### Етап 4: Кешування
1.  Розглянути впровадження Hibernate 2nd Level Cache (Ehcache або Redis) для статичних довідників та популярних постів.

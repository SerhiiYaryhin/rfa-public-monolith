# Пропозиція: Універсальний інструмент завантаження файлів (2026-05-09)

## Концепція
На основі аналізу існуючих контролерів завантаження (`CreaterDropPostFileController`), пропонується впровадження єдиного універсального REST-ендпоінту для роботи зі сховищем. Це дозволить уникнути дублювання коду для різних типів контенту (треки, обкладинки, фото профілю тощо).

## Технічне рішення

### 1. Універсальний REST-ендпоінт
Пропонується створити метод `/api/store/upload`, який прийматиме:
*   `file`: власне медіа-файл.
*   `type`: рядок, що відповідає одному зі значень `EStoreFileType` (наприклад, `STORE_TRACK`, `STORE_ALBUMCOVER`).

### 2. Приклад реалізації на Backend (Java)
```java
@PostMapping(path = "/api/store/upload")
public ResponseEntity<?> universalUpload(
        @RequestParam("file") MultipartFile file,
        @RequestParam(value = "type", defaultValue = "STORE_FILE") String type) {
    
    // Валідація та перевірка прав
    Clientdetail cd = clientService.GetClientDetailByUser(clientService.GetCurrentUser());
    if (!clientService.ClientCanDownloadFile(cd)) {
        return ResponseEntity.status(HttpStatus.FORBIDDEN).body(Map.of("error", "Access denied"));
    }

    try {
        // Конвертація рядка у Enum
        EStoreFileType fileType = EStoreFileType.valueOf(type);
        
        // Збереження у фізичне сховище та БД (таблиця Store)
        String storeUUID = storeService.PutFileToStore(file.getInputStream(), file.getOriginalFilename(), cd, fileType);
        
        return ResponseEntity.ok(Map.of(
            "success", true,
            "uuid", storeUUID,
            "url", "/store/content/" + storeUUID,
            "filename", file.getOriginalFilename()
        ));
    } catch (Exception e) {
        return ResponseEntity.internalServerError().body(Map.of("error", e.getMessage()));
    }
}
```

## Принцип роботи (Workflow)

Процес завантаження медіа-контенту виглядатиме наступним чином:

1.  **Дія користувача:** Автор обирає файл у будь-якій формі (наприклад, редагування треку).
2.  **Запит клієнта:** JavaScript-код (на базі Dropzone або Fetch API) відправляє асинхронний POST-запит на `/api/store/upload`. У запиті обов'язково вказується параметр `type=STORE_TRACK` (або інший, залежно від контексту).
3.  **Обробка сервером:** 
    *   Контролер перевіряє авторизацію та права клієнта на завантаження.
    *   `StoreService` зберігає файл на диску (або в хмарне сховище) та створює запис у таблиці `Store`.
    *   Система автоматично генерує унікальний UUID для файлу.
4.  **Відповідь:** Сервер повертає JSON-об'єкт із метаданими завантаженого файлу (UUID, URL, ім'я).
5.  **Завершення на клієнті:** Фронтенд отримує UUID та оновлює поле у відповідній сутності (наприклад, призначає цей UUID як `storeuuid` треку) або просто відображає прев'ю.

## Особливості реалізації для проекту RFA

Реалізація цього інструменту враховує специфічні потреби нашої платформи:

*   **Інтеграція з безпекою:** Використання існуючого механізму `clientService.GetCurrentUser()` для жорсткої прив'язки кожного файлу до `Clientdetail`. Файли одного автора ніколи не перетнуться з файлами іншого.
*   **Автоматичне видалення старих версій:** В універсальний ендпоінт буде закладено логіку заміни: якщо при завантаженні передано `entityId`, система знайде попередній файл цієї сутності та фізично видалить його зі сховища, економлячи місце на сервері.
*   **Підтримка профілів:** Контролер працюватиме під профілем `@Profile("Front")`, забезпечуючи доступність функціоналу саме на публічній частині сайту.
*   **Уніфікований обробник помилок:** Всі винятки (IO, права доступу, перевищення ліміту розміру) повертатимуть структурований JSON, що дозволить відображати гарні сповіщення (toastr) на фронтенді.

## Компоненти та форми для використання

Впровадження універсального завантажувача відбуватиметься поетапно, відповідно до стратегії переходу проекту на нові інструменти редагування:

1.  **Editor.js (Поточний етап - Статті авторів):** Використовується в "Колонці автора" (`AuthorArticle`). Універсальний інструмент забезпечить надійне завантаження ілюстрацій всередині блоків тексту, створення галерей та вкладення файлів.
2.  **Форми редагування медіа (Поточний етап):**
    *   Редактор треків (`edittrack.html`): Для завантаження аудіофайлів (`STORE_TRACK`).
    *   Редактор альбомів (`editalbum.html`): Для управління обкладинками альбомів (`STORE_ALBUMCOVER`).
    *   Профіль користувача (`profile.html`): Для зміни фото профілю (`STORE_PHOTO`).
3.  **Перспективний етап (Міграція Постів):** Коли розпочнеться процес конвертації та переходу основних Новин/Постів (`Post`) з TinyMCE на Editor.js, універсальний інструмент стане базою для автоматизованого переносу зображень зі старого формату в блоки нового редактора.
4.  **Адміністрування та Реклама:**
    *   Менеджер баннерів: Для завантаження рекламних медіа-матеріалів.
    *   Глобальне Сховище: Як основний механізм пакетного завантаження.

## Переваги підходу
1.  **Чистота коду:** Замість 10 різних методів (`uploadTrack`, `uploadAlbumCover`, `uploadPicProfile`...) ми маємо один надійний механізм.
2.  **Гнучкість фронтенду:** Один JavaScript-компонент може обслуговувати весь сайт, змінюючи лише один параметр `type`.
3.  **Легке розширення:** При додаванні нових типів файлів у систему не потрібно вносити зміни в контролери завантаження.
4.  **Стандартизація відповідей:** Усі клієнтські додатки отримують JSON однакової структури, що спрощує обробку помилок та індикацію прогресу.

## Подальші кроки
У перспективі цей інструмент можна розширити для **автоматичного зв'язування з сутностями**. Наприклад, передаючи `entityUuid` та `entityType`, сервіс зможе не лише завантажити файл, а й одразу призначити його обкладинкою для конкретного альбому чи поста, видаливши старий файл за один транзакційний крок.

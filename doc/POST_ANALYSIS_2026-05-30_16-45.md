# Звіт про аналіз функціоналу роботи з постами
**Дата та час:** 2026-05-30 16:45
**Проект:** RFA (Radio Toloka)

## 1. Огляд наявного функціоналу

На основі аналізу коду (`PostController`, `PostListController`, `AdminPosts`, `Post.java`) встановлено поточний стан системи:

### А. Для авторизованих користувачів (Авторів/Креаторів):
*   **Створення:** Реалізовано через `/creater/editpost/0`. Використовується редактор TinyMCE. Початковий статус — `POSTSTATUS_REDY`.
*   **Редагування:** Реалізовано через `/creater/editpost/{uuidPost}`. Дозволяє змінювати заголовок, лід, категорію та вміст.
*   **Публікація (Запит):** Реалізовано через переведення статусу в `POSTSTATUS_REQUEST`. Обов'язковою умовою є наявність головної ілюстрації (`coverstoreuuid`).
*   **Видалення:** Реалізовано як "м'яке видалення" (soft delete) шляхом встановлення статусу `POSTSTATUS_DELETE`.
*   **Зняття з публікації:** Окремої кнопки немає, але технічно можливо через зміну статусу назад на `POSTSTATUS_REDY` у формі редагування.

### Б. Для адміністраторів:
*   **Модерація:** Адмін бачить список усіх постів. Може схвалити (`apruve = true`, статус `POSTSTATUS_PUBLICATE`) або відхилити (`apruve = false`, статус `POSTSTATUS_REJECT`).
*   **Керування:** Можливість повного видалення або примусової публікації.

### В. Для незареєстрованих користувачів (Гостей):
*   **Відображення списку:** Реалізовано через `/guest/postall`. Фільтрація відбувається за прапорцем `apruve = true`.
*   **Перегляд поста:** Реалізовано через `/post/postview/{uuidPost}`. При кожному перегляді інкрементується лічильник `looked`.

## 2. Виявлені недоліки та ризики

1.  **Безпека (Критично):** У `PostController` відсутня перевірка власності. Будь-який авторизований користувач може відредагувати або видалити чужий пост, знаючи його UUID.
2.  **Дублювання логіки статусів:** Використовується одночасно булеве поле `apruve` та енум `EPostStatus`. Це призводить до розсинхронізації (наприклад, пост може мати статус `POSTSTATUS_PUBLICATE`, але `apruve = false`).
3.  **Логіка створення нового поста:** Використання UUID як ідентифікатора в URL ще до збереження в БД є робочим, але нетиповим підходом, що може викликати проблеми при збоях транзакцій.
4.  **Відсутність "Відклику":** Автор не має простої можливості "відкликати" пост із черги на модерацію одним натисканням.
5.  **Фільтрація для гостей:** Пошук публічних постів базується лише на `apruve = true`, без врахування статусу `POSTSTATUS_DELETE` або дати закінчення публікації (`enddate`).

## 3. Рекомендації

1.  **Впровадити Ownership Check:** Додати перевірку `post.clientdetail.user == currentUser` у всіх методах редагування та видалення.
2.  **Гармонізація статусів:** Зробити `apruve` похідним від статусу або жорстко зв'язати їх у `PostService`.
3.  **Додати функцію "Зняти з публікації" (Unpublish):** Створити окремий endpoint для швидкого переведення поста в стан чернетки.
4.  **Покращити фільтрацію:** Врахувати `enddate` та виключити видалені пости з публічного перегляду.
5.  **Логування:** Додати історію змін статусів для аудиту (хто і коли схвалив/відхилив).

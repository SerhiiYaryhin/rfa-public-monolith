## 1. Нова архітектура: Образи дисків (`.img`)

Згідно з новим підходом, усі файли кожної радіостанції тепер ізольовані всередині окремих образів дисків. Це забезпечує жорсткі дискові квоти та спрощує перенесення або повне видалення даних.

### Ключові аспекти керування образами:
*   **Створення**: Використання `truncate` для створення розріджених (sparse) файлів (наприклад, 10G), які займають місце на фізичному диску лише по мірі заповнення.
*   **Ізоляція**: Кожна станція має свій `storage.img`, що монтується як `loop` пристрій у каталог станції.
*   **Монтування**: Реєстрація в `/etc/fstab` для збереження стану після перезавантаження сервера.

## 2. План переходу на Ansible (Playbooks)

Всі необхідні інструкції вже перенесено до каталогу `playbooks/` у корені проекту.

### 2.1. Створення та розгортання (`playbooks/create_station_full.yml`)
Плейбук реалізує повний цикл підготовки:
1.  **Disk Setup**: Створення файлу-образу, форматування в `ext4` та монтування у точку `/libretime`.
2.  **External Services**: Делегування завдань на сервери PostgreSQL та RabbitMQ для створення ізольованих БД та черг.
3.  **Dockerization**: Генерація `docker-compose.yml` на основі Jinja2 шаблонів та запуск контейнерів.
4.  **Network**: Налаштування зовнішнього Nginx Gateway для проксіювання трафіку на конкретну станцію.

### 2.2. Безпечне видалення (`playbooks/delete_station_with_quota.yml`)
Плейбук гарантує повне очищення ресурсів:
1.  **Graceful Stop**: Зупинка Docker-контейнерів.
2.  **Unmount**: Безпечне розмонтування образу диска та видалення запису з `fstab`.
3.  **Physical Cleanup**: Видалення файлу `.img` та всього каталогу станції.
4.  **Remote Cleanup**: Видалення БД, користувачів та VHost-ів на відповідних серверах.

## 3. Рекомендації щодо впровадження

1.  **Динамічні змінні**: Java-код (через `ServerRunnerService`) повинен генерувати JSON-файл із параметрами (`client_uuid`, `station_uuid`, `db_server_ip` тощо) та передавати його в Ansible через `--extra-vars`.
2.  **Атомарність**: Запуск видалення станції в БД RFA (статус `DELETING`) має відбуватися ПЕРЕД запуском плейбука `destroy.yml`.
3.  **Обробка помилок**: Необхідно врахувати випадок, коли диск уже розмонтований або файл образу відсутній (`ignore_errors: yes` у критичних місцях, що вже впроваджено в плейбуки).
4.  **Безпека**: Відмова від `root` доступу на користь обмеженого користувача `ansible-worker` з налаштованим `sudo`.

## 4. Порівняльна таблиця: Shell vs Ansible (Image-based)

| Функція | Поточний (Shell) | Пропонований (Ansible) |
| :--- | :--- | :--- |
| **Квоти** | Відсутні / Складні | Жорсткі (через .img файли) |
| **Ідемпотентність** | Відсутня | Повна (state: present/absent) |
| **Помилки** | Продовжує виконання | Негайна зупинка (fail-fast) |
| **Безпека** | Прямий SSH root доступ | Керування через обмеженого юзера |

---

## 5. Висновок

Використання образів дисків у поєднанні з Ansible робить інфраструктуру Толоки набагато надійнішою. Тепер ми маємо чітко визначені межі для кожної станції, а плейбуки в каталозі `playbooks/` забезпечують автоматизацію, яку легко підтримувати та масштабувати.

# Технічний аналіз взаємодії з радіостанціями через RabbitMQ
**Дата:** 11 червня 2026 р.
**Час:** 20:31
**Статус:** Аналіз архітектури RPC (Remote Procedure Call)

## 1. Загальна архітектура
Система використовує асинхронну модель керування радіостанціями на основі протоколу AMQP (RabbitMQ). Це дозволяє основному додатку RFA відправляти складні команди на віддалені сервери мовлення, не очікуючи їх завершення в реальному часі.

### Ключові компоненти:
*   **Message Broker**: RabbitMQ.
*   **Data Format**: JSON (серіалізація через `Gson`).
*   **Job Container**: Клас `RPCJob`, що містить ланцюжок завдань (`jobchain`), дані об'єкта (`rjobdata`) та контекст користувача.

---

## 2. Процес ініціації (Producer)

Основним механізмом відправки команд є метод `triggerJob` у сервісі `StationService`.

*   **Клас**: `media.toloka.rfa.radio.station.service.StationService`
*   **Метод**: `public void triggerJob(Station station, Users user, ERPCJobType... types)`
*   **Логіка**:
    1.  Створює об'єкт `RPCJob`.
    2.  Додає перелік типів робіт (`ERPCJobType`) у чергу `jobchain`.
    3.  Серіалізує об'єкт `Station` у JSON-рядок та кладе в `rjobdata`.
    4.  Відправляє повідомлення в чергу через `rabbitTemplate.convertAndSend`.

---

## 3. Процес обробки (Consumer / Worker)

Воркер на боці сервера (або внутрішній компонент у поточній конфігурації) слухає чергу та виконує команди ОС.

*   **Клас**: `media.toloka.rfa.rpc.RPCListener`
*   **Метод**: `@RabbitListener(queues = "${rabbitmq.queue}") public void processedFromFront(String message)`
*   **Логіка**:
    1.  Отримує JSON, десеріалізує його в `RPCJob`.
    2.  Витягує перше завдання з ланцюжка (`rjob.getJobchain().poll()`).
    3.  Використовує `Switch-Case` для вибору відповідного методу в `ServerRunnerService`.
    4.  Після завершення викликає `CompletedPartRPCJob`, який перевіряє, чи залишилися завдання в ланцюжку, і якщо так — відправляє `RPCJob` назад у чергу для наступного кроку.

---

## 4. Виконавчий рівень (Executors)

Клас `ServerRunnerService` відповідає за безпосередню взаємодію з операційною системою через `ProcessBuilder`.

*   **Клас**: `media.toloka.rfa.rpc.service.ServerRunnerService`
*   **Основні методи**:
    *   `AllocateStationOnServer`: Створює структуру каталогів та базові конфіги (скрипт `createStation.sh`).
    *   `StationMigrateLibretimeOnInstall`: Виконує початкову міграцію БД Libretime.
    *   `StationPrepareNginx`: Формує та записує конфігураційний файл Nginx.
    *   `StationStart / StationStop`: Запускає/зупиняє Docker-контейнери станції.
    *   `StationDelete`: Видаляє фізичні ресурси станції (скрипт `deleteStation.sh`).

---

## 5. Зворотний зв'язок (Callback)

Для операцій, що потребують відповіді (наприклад, список запущених процесів), використовується механізм Callback-черг.

*   **Клас**: `media.toloka.rfa.rpc.BackRPCResponce`
*   **Черга**: `${media.toloka.rfa.server.libretime.guiserver}.callback`
*   **Приклад**: Команда `JOB_GETRUNSTATIOM` повертає список імен запущених контейнерів у форматі JSON.

---

## 6. Виявлені особливості та рекомендації

1.  **Рекурсивна обробка**: Використання `jobchain` дозволяє створювати складні послідовності дій (наприклад: Створити -> Розмістити -> Мігрувати -> Запустити) одним викликом.
2.  **Слабке місце**: Поточна реалізація `CompletedPartRPCJob` просто шле об'єкт далі в чергу. Якщо один із проміжних кроків завершився з помилкою (exit code != 0), система все одно намагається виконати наступний крок, що може призвести до непередбачуваних станів.
3.  **Рекомендація**: Додати перевірку результату попереднього кроку в `RPCListener` перед виконанням `poll()` для наступного завдання.
4.  **Безпека**: Паролі та чутливі дані передаються в `rjobdata` як частина JSON. Варто розглянути шифрування корисного навантаження (payload) для багатосерверних конфігурацій.

---

## 7. Аналіз Shell-файлів керування (`src/main/resources/ShellFiles`)

Для виконання низькорівневих операцій система використовує набір bash-скриптів, які викликаються через `ProcessBuilder` у `ServerRunnerService`.

### Ключові виявлені особливості:
*   **Тісна прив'язка до оточення**: Скрипти (наприклад, `createStation.sh`) критично залежать від великої кількості змінних середовища (`CLIENT_DIR`, `STATION_UUID` тощо), що передаються з Java-коду.
*   **Використання шаблонізації**: Активно використовується утиліта `envsubst` для підстановки значень у шаблони конфігураційних файлів (`config.yml`, `docker-compose.yml`, `nginx.conf`).
*   **Дистанційне керування (SSH/SCP)**: Багато скриптів виконують команди на віддалених серверах (`ssh root@$HOST`) та копіюють файли (`scp`). Це вказує на розподілену архітектуру, але створює ризики безпеки.
*   **Відсутність обробки помилок**: Більшість скриптів не перевіряють статус виконання попередніх команд (немає `set -e` або перевірок `$?`), що підсилює проблему "сліпого" виконання ланцюжка завдань.

### Рекомендації щодо зміни підходу:

1.  **Впровадження Configuration Management**: Замість розрізнених shell-скриптів доцільно перейти на використання **Ansible** або подібних інструментів. Це забезпечить ідемпотентність операцій та кращу діагностику помилок.
2.  **Шаблонізація на рівні Java**: Використовувати вбудовані в Java двигуни шаблонів (наприклад, **Freemarker** або **Mustache**) для генерації конфігураційних файлів. Це зробить логіку генерації більш прозорою та тестованою, прибравши залежність від системної утиліти `envsubst`.
3.  **Безпека та обмеження прав**:
    *   Відмовитися від виконання команд під користувачем `root` через SSH.
    *   Використовувати обмежені облікові записи для конкретних задач (наприклад, для керування RabbitMQ або PostgreSQL).
4.  **Покращення обробки помилок**: Кожен скрипт має повертати чіткі коди помилок. В Java-коді (`ServerRunnerService`) необхідно аналізувати результат `p.waitFor()` і переривати `jobchain`, якщо крок завершився з помилкою.
5.  **Централізація секретів**: Паролі та ключі доступу не повинні передаватися у відкритому вигляді через змінні оточення. Рекомендовано використовувати **Spring Cloud Config** або **HashiCorp Vault**.

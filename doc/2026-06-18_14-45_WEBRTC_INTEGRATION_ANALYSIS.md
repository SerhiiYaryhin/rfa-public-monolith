# Аналіз інтеграції WebRTC сервісу (18.06.2026 14:45)

## 1. Загальний огляд архітектури
Інтеграція побудована за сучасною розподіленою схемою, що забезпечує високу гнучкість та масштабованість. Основні компоненти:
*   **Медіасервер Janus (janus.rfa):** Використовується плагін `audiobridge` для мікшування голосу учасників чату та трансляції радіоефіру.
*   **CoTURN (gate.rfa):** Забезпечує NAT traversal (STUN/TURN), що критично для роботи WebRTC у реальних мережах.
*   **RabbitMQ:** Виступає центральною шиною для команд. Використання патерну RPC (Request-Reply) для взаємодії з Janus через RabbitMQ — це відмінне рішення, яке знімає потребу у прямих HTTP-з'єднаннях між сервісами.
*   **Python FFmpeg Agent:** Спеціалізований агент для перекодування аудіопотоків радіостанцій (Icecast/MP3) у формат Opus/RTP для "впорскування" в Janus.

## 2. Аналіз програмного коду (Java)

### JanusRabbitClient.java
*   **Переваги:** Чиста реалізація RPC через `RabbitTemplate`. Використання `admin_secret` та механізму токенів (`registerUserToken`) забезпечує належний рівень безпеки.
*   **Функціональність:** Повністю реалізовано життєвий цикл кімнати: створення, реєстрація користувачів, керування мікрофонами (mute/unmute).
*   **Рекомендація:** Винести параметри аудіо (48000Hz, стерео) у конфігураційний файл, хоча поточні значення є стандартом для WebRTC.

### RadioLiveService.java & PortAllocationService.java
*   **Переваги:** Чіткий розподіл відповідальності. `PortAllocationService` надійно запобігає конфліктам UDP-портів, зберігаючи стан у базі даних (entity `JanusLiveStream`).
*   **Функціональність:** Метод `startBroadcast` успішно поєднує створення кімнати в Janus та запуск FFmpeg через чергу повідомлень.

### Конфігурація
*   Використання `GsonAmqpMessageConverter` забезпечує коректну серіалізацію складних об'єктів для Janus.

## 3. Аналіз FFmpeg Агента (Python)

### rfa-ffmpeg-agent.py
*   **Переваги:** Перехід на RabbitMQ (замість HTTP у старій версії `agent.py`) значно підвищує надійність системи. Агент використовує `subprocess.Popen` з коректною обробкою сигналів завершення (`terminate`/`kill`).
*   **Параметри FFmpeg:** Налаштування `-re`, `-acodec libopus`, `-f rtp` підібрані оптимально для мінімізації затримок.

## 4. Висновки та рекомендації

### Сильні сторони:
1.  **Розподіленість:** Система готова до розгортання в Docker/Kubernetes оточенні.
2.  **Стандартизація:** Використання кодека Opus та частоти 48кГц забезпечує найкращу якість звуку в WebRTC.
3.  **Безпека:** Реалізовано авторизацію через токени на рівні медіасервера.

### Рекомендації до покращення:
1.  **Очищення застарілого коду:** Рекомендується видалити `FFmpegAgentClient.java` та `agent.py`, якщо перехід на RabbitMQ остаточний, щоб не плутати розробників.
2.  **Обробка помилок:** У Java-сервісах варто замінити загальні `RuntimeException` на кастомні виключення для кращої діагностики на рівні API.
3.  **Health Checks:** Додати механізм перевірки "здоров'я" (Health Check) для Janus та Python-агента, щоб Spring Boot міг знати, чи готові вони приймати нові стріми.
4.  **Моніторинг портів:** Хоча діапазон 10000-15000 великий, варто додати алерт при заповненні >80% доступних портів.
5.  **Відновлення після збоїв:** Python-агент наразі зберігає активні стріми лише в пам'яті. Якщо агент перезавантажиться, він не знатиме про запущені раніше FFmpeg (хоча Spring Boot має PID в БД). Варто реалізувати механізм синхронізації стану при запуску агента.

**Загальна оцінка:** Код написаний на високому професійному рівні, архітектурно виважений та готовий до фінальної відладки на `test.rfa.toloka.media`.
